# Contributions Inbox

A holding area for generic improvements contributed back from real projects when no pull-request workflow is available. Entries here are **not yet applied** — a maintainer folds each one into its proper template/shared file (see [CONTRIBUTING.md](CONTRIBUTING.md) → "Where it goes") and then removes it from this file.

**This is a queue, not a home.** A change isn't "done" while it's only in the inbox.

## Auto-resolving a merge conflict: verify in memory, gate the write (2026-09-01)

When a script resolves a known-shape conflict (e.g. a keep-both union of a changelog's unreleased section), every safety check must run on the resolved text IN MEMORY and gate the write and the commit; a check that runs after `writeFileSync` is decoration. Observed: a placement check threw a false positive after the file was already written, `set -e` did not stop the else-branch it lived in, and the merge was committed and pushed anyway — the union happened to be correct, the process was not. Two rules: (1) build the resolution, assert (no markers; every conflict-region line inside the intended section; everything after the section byte-identical to base), THEN write, add, commit — with no auto-commit path past a failed assertion; (2) never prove placement by grepping the whole file for the new content's keywords — frozen history contains every word you will pick; assert the untouched region is identical to `{{BASE_REF}}` instead.

### 2026-09-04 — A missing or unauthenticated MCP server is not a block when the project's own hook library already speaks the REST API

- **Trigger:** a forked follow-up session had no `{{MCP_SERVER}}` tools (the plugin showed "Needs authentication" and the machine was OAuth-enrolled, so the documented curl-with-bearer fallback could not work either). The session's SessionStart hook had nonetheless "registered" it on the bus, which meant the repo already shipped a library that resolves the service bearer from the secrets manager and wraps the HTTP calls. Importing that library from a scratch script gave every tool's REST equivalent in one turn, with no sign-in and no restart.
- **Is it generic?** Yes. Stripped: the bus product, the secrets manager, the route names, the Windows quoting detail. Kernel: (1) before declaring an MCP layer unreachable, look for the project's own hook or script code that talks to the same service, because hooks that run without a model must carry a credential path of their own; (2) reuse that module rather than re-deriving auth; (3) wrap it as a tiny CLI (`METHOD path @bodyfile`) with bodies read from files, because shells that strip quotes from inline JSON produce silent 400s; (4) long-running server jobs started over REST are polled from a background process loop, never from the model loop.
- **Target:** a new tagged lesson under `lessons/` (tags: mcp, auth, self-heal, hooks, orchestration); cross-link any lesson about not timer-polling from the model loop.
- **Proposed change:** lesson text: "**An unauthenticated MCP server is a convenience layer that went missing, not a wall.** Before asking a human to sign in, grep the repo's hooks and scripts for the module that already calls the same service (`{{HOOK_LIB}}`, `{{BEARER_RESOLVER}}`); a hook that runs with no model attached must resolve its own credential, and that module is the fastest correct client. Wrap it as `{{CLIENT}} METHOD /api/path @body.json` (bodies from files, never inline JSON), confirm one read route answers, then use the REST equivalents of every tool you needed. Poll server-side runs from a background loop with a fixed interval, and re-fetch state at your next natural turn."
- **Applied?** `no`

### 2026-09-01 — A `position: fixed` overlay cannot make the page scroll; a body-level overflow "during the overlay" is a defect in the layout underneath

- **Trigger:** a ~17px body-level scroll at the smallest supported phone viewport was noticed while a fullscreen tour panel was showing, and was attributed (in a spec comment and a playbook note) to the panel's plain `92vh` height cap. Measured on the base branch, `document.scrollHeight` equalled the viewport at every panel step. The overflow only reproduced with a normal-flow top banner present, whose height CSS variable was written from a `ResizeObserver` callback's `entry.contentRect.height` (content box) while the page subtracted it from a border-box height: `{{VIEWPORT_H}} - {{CONTENT_BOX_H}} + {{BORDER_BOX_H}}` matched the measured overflow to the pixel (padding + border was the whole gap).
- **Is it generic?** Yes. Stripped: the app, the tour library, the banner, the viewport numbers. Kernel: (1) `position: fixed` (and modal top-layer) elements add nothing to the document's scrollable overflow, so `scrollHeight > innerHeight` while such an overlay is up is never the overlay: walk the normal-flow chain (`html`, `body`, app root, layout, page) and find the box taller than the viewport, then compare the number it was GIVEN with the number it RENDERS; (2) `ResizeObserver` `contentRect` excludes padding and border, so when the value feeds a subtraction from a border-box height, read `entry.borderBoxSize?.[0]?.blockSize ?? el.getBoundingClientRect().height`; (3) a polled `scrollHeight <= innerHeight` assertion at the overlay steps cannot pass vacuously and pins the misattribution out for good.
- **Target:** a new tagged lesson under `lessons/` (tags: css, layout, resize-observer, e2e, diagnosis); cross-link `read-which-error-fired-before-theorising` (same shape: the suspect named by the symptom was not the cause).
- **Proposed change:** lesson text — "**An overlay that is `position: fixed` cannot make the page scroll.** When `document.scrollHeight` exceeds the viewport while a fixed overlay is showing, the defect is in the normal-flow layout underneath: walk `html -> body -> app root -> layout -> page`, find the box taller than the viewport, and compare what it was given with what it renders. A common culprit is a height CSS variable fed from `ResizeObserver` `entry.contentRect.height`, which excludes padding and border; if the consumer subtracts it from a border-box height, read `entry.borderBoxSize?.[0]?.blockSize` (fallback `getBoundingClientRect().height`). Pin the invariant with a polled `scrollHeight <= innerHeight` assertion at the overlay steps so the next reader does not re-blame the overlay."
- **Applied?** `no`

### 2026-09-01 — A hash-only Playwright `goto` fired before the SPA router's first navigation finalizes is silently dropped; settle the first page before the second navigation

- **Trigger:** an E2E test seeded a browser-history entry with `page.goto('/#/first')` and immediately called `page.goto('/#/second?x=1')`. Roughly one attempt in three the URL changed, the first page stayed rendered, the second route's module was never requested, and the retry passed, so it read as a load flake. The trace showed the second `goto` landing while the first route's lazy chunk was still loading. Vue Router only starts reacting to popstate once `markAsReady()` runs at the end of the first navigation (the DOM listener exists from history creation; the router's own `.listen()` callback is what `markAsReady` registers), so a same-document hash change inside that window is ignored.
- **Is it generic?** Yes. Stripped: the app, the test ids, the route names. Kernel: `page.goto` to a hash URL resolves on `load`, which fires before an SPA has booted and before its router's initial navigation has finalized; a second hash-only `goto` in that window is a same-document navigation the router may not react to yet. Sibling tests in the same file already waited for the first page's root element before navigating again; the flaky one did not.
- **Target:** a new tagged lesson under `lessons/` (tags: playwright, e2e, spa-router, flake); cross-link any lesson on "passes on retry is not evidence of a load flake; read the trace".
- **Proposed change:** lesson text — "**Before a second hash navigation in a Playwright test, wait for the first page to actually render.** `page.goto('/#/first')` resolves on `load`, while the SPA is still booting and its router's initial navigation is in flight; a following `page.goto('/#/second')` is a same-document hash change the router does not react to yet (Vue Router: until `markAsReady()` at the end of the first navigation): URL updated, page unchanged, next route never requested. Assert the first page's root element is visible (`await expect(page.locator('{{FIRST_PAGE_ROOT}}')).toBeVisible()`) before the second `goto`. A first-attempt-only failure at the second page's first expectation is the tell; confirm from the trace that the second route's module was never fetched."
- **Applied?** `no`

### 2026-09-01 — Windows PowerShell 5.1 `-Encoding utf8` writes a BOM; commit-message files (and anything parsed at byte 0) must be written BOM-free

- **Trigger:** an agent wrote a commit message to a file with `Set-Content -Encoding utf8` and ran `git commit -F <file>`; commitlint rejected it with an "empty header" error because the UTF-8 BOM was read as the first character of the subject line. The retry with a BOM-free writer went through unchanged.
- **Is it generic?** Yes. Stripped: the project, the commit subject, the hook name. The reusable kernel: on Windows PowerShell 5.1, `Set-Content`/`Out-File -Encoding utf8` emit a BOM (PowerShell 7 does not), and any consumer that parses from byte 0 (commitlint, strict JSON parsers, hook stdin files, `.gitmessage`) sees a phantom character. The failure reads as a content error ("empty header", "unexpected token"), never as an encoding error.
- **Target:** a new tagged lesson under `lessons/` (tags: windows, powershell, git, encoding), cross-linked from whichever Windows agent template tells agents to use `git commit -F <file>` because the shell mangles quotes.
- **Proposed change:** lesson text — "**On Windows PowerShell 5.1, write commit-message files (and any file a strict parser reads from byte 0) BOM-free:** `[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding $false))`. `Set-Content -Encoding utf8` / `Out-File -Encoding utf8` prepend a UTF-8 BOM there (PowerShell 7 does not), and commitlint, strict JSON parsers, or hook inputs then reject the file with a misleading content error such as 'empty header' or 'unexpected token', never an encoding error."
- **Applied?** `no`
